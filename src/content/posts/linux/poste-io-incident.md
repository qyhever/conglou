2026 年 11 月 23 日早晨，通过 ssh 连接 VPS，发现连接时间过长，成功进入 VPS 后，发现内存爆满，根本输入不了命令。这台运行 Poste.io 的双核 VPS 持续过载。北京时间 08:00-09:00，CPU 平均使用率约 **97%**，Swap 几乎用尽，内核 **53 次**因内存不足杀死进程。把这些事件逐条对应到 Docker 容器后，所有被杀进程都指向同一个地方——邮件容器 `poste`。

沿着容器里的挖矿程序和 PHP 后门回查，SMTP 日志把线索带到了两天前的一封 DMARC 报告邮件。结合公开漏洞公告，**Poste.io 的 DMARC 报告处理漏洞 `CVE-2026-127027` 是这次入侵的高置信度入口**。文中时间统一为北京时间（UTC+8）。

## 从资源异常找到出问题的容器

登录服务器时，早晨的资源尖峰已经过去。此时的进程列表只能反映眼下的负载，所以先用 `sar` 回看历史采样，再用 `journalctl --list-boots` 确认重启时间。08:50 左右，系统可用内存只剩约 **8 MiB**。09:06，机器重启。

关键记录在上一轮启动的内核日志里。每次 OOM（内存不足）都会留下被杀进程、用户 ID、内存占用和所属的 cgroup。08:00-09:00 的 53 个受害进程全在 `poste` 的 Docker cgroup，用户 ID 都是 33，单个进程占用的匿名常驻内存约 **1.7 GiB**。进程名一直在变，内存规模却相近。重启后，同类进程再次触发了 OOM。

## 从容器文件和运行中的进程找到后门

接下来用 `docker diff` 查看容器可写层的变动，再检查仍在运行的进程和它们打开的文件。这两条线索各找到一个样本。

| 线索 | 发现 |
| --- | --- |
| 容器可写层 | 在 ACME 证书验证目录的隐藏子目录中找到 `mknodd`。这个 Linux 可执行文件包含 `XMRig 6.26.0`、RandomX 和 Monero 标识。 |
| 进程的打开文件 | 一个以 `www-data` 身份运行的 shell 仍持有已经删除的 `psap50m7.php`。通过进程的文件描述符保留了样本。静态检查显示，它能根据 HTTP 请求参数执行 shell 命令。 |

两个样本都计算并核验了 SHA-256。ClamAV 对它们均未告警，这次确认依赖的是二进制特征、脚本行为和运行时证据。宿主机及容器重点路径的定向扫描未发现更多恶意文件。扫描跳过了超过 25 MiB 的文件，也没有覆盖全部历史邮件附件。

## 用 SMTP 和 Web 日志追查入口

在旧数据卷中，DMARC 报告日志目录里出现了指向 Web 目录的异常符号链接。沿着链接上的文件名回查，它同时出现在 Haraka 的 SMTP 投递记录和 Nginx 的访问记录中。三种记录的时间可以对齐。

| 时间 | 证据 |
| --- | --- |
| 11 月 21 日 19:56:41 | SMTP 投递日志记录了一笔发往 DMARC 报告地址的事务，附件记录包含 `psap50m7.php`。 |
| 11 月 21 日 19:56:42 | DMARC 报告目录中的同名符号链接带有这一时间戳，目标指向 Web 目录中的 `psap50m7.php`。 |
| 11 月 21 日 19:57:03 | Nginx 记录该 PHP 路径收到访问，返回 HTTP 200。 |
| 11 月 21 日 19:58:27 | 保留的内核日志首次记录相关进程触发 OOM。 |
| 11 月 23 日 08:00-09:00 | 资源压力持续，内核反复杀死 `poste` 容器里的进程。 |
| 11 月 23 日 09:06、10:20 | VPS 重启后，同一后门路径再次收到访问，随后又出现同类 OOM。 |

这条证据链把 SMTP 附件、DMARC 目录、PHP 后门和资源异常连在一起。它支持对本次入侵入口的判断。是否存在更早的入侵，以及容器内的数据是否被读取或外传，仍未确认。宿主机的定向检查也暂未发现提权迹象。

## 漏洞公告与现场证据的对应关系

CERT Polska 于 **2026 年 11 月 20 日**公布 `CVE-2026-127027`。Poste.io 在处理 DMARC 聚合报告时，会解包通过 SMTP 收到的附件。受影响版本的解包流程存在操作系统命令注入，可让未经认证的远程发件人在 **Poste.io 容器内**以 root 权限执行命令。受影响范围是 **低于 `2.5.22`** 的版本。 [CERT Polska 漏洞公告](https://cert.pl/en/posts/2026/11/CVE-2026-127027/)

现场证据与公告描述的入口一致。旧实例属于受影响范围，发往 DMARC 报告地址的事务与后门使用了同一个文件名，随后 Web 日志又记录了对该文件的访问。这里的归因来自已归档的日志与文件，具体攻击载荷未做复现。

## 隔离、重建和恢复验证

先关闭旧容器的自动重启并停止它，再保留容器可写层、原始数据卷、投递与访问日志以及恶意样本。邮件服务用已修补的官方 **`2.5.26`** 镜像重建，并把 Compose 配置固定到镜像摘要，便于核对实际运行版本。 [Poste.io 官方更新记录](https://poste.io/changelog)

新实例迁移了邮箱、队列和业务配置，清除了旧 Webmail 会话。原始日志、旧 Redis 状态和包含可疑链接的 DMARC 目录留在归档中。容器健康检查通过，三个邮件域的 Webmail 在公网验证中返回 HTTP 200，SMTP STARTTLS 与 IMAPS 握手通过。公网 SMTP 25 端口从部分测试来源连接超时，本次验证未实际投递测试邮件。

## 后续加固优先级

1. **轮换容器可访问的凭据。** 优先处理管理和邮箱密码，以及容器可读取的 TLS、DKIM 私钥。复核异常登录、转发地址与 Sieve 规则。
2. **缩小邮件服务暴露面。** 将 DMARC 聚合报告交给独立收集服务，或在不需要报告时停用本机收集并保留域的 DMARC 策略。公网 SMTP 25 继续用于接收正常邮件。管理入口限制到 VPN 或可信地址，反向代理的后端端口按实际依赖收紧绑定。 [Docker 防火墙文档](https://docs.docker.com/engine/network/packet-filtering-firewalls/)
3. **限制容器权限与资源。** 验证邮件业务对额外 Linux capabilities 的依赖，移除用不到的权限。用实测的邮件负载和 ClamAV 更新峰值设定 CPU、内存和进程数限制，给宿主机留出余量。 [Docker 资源限制文档](https://docs.docker.com/engine/containers/resource_constraints/)
4. **让下一次异常更早被看到。** 把持续高 CPU、Swap 增长和容器 OOM 加入监控。异机留存 SMTP、Web 和容器日志，订阅厂商安全公告，并定期验证备份能否恢复。

如果同一容器反复出现 OOM，可以先从内核日志的 cgroup 找到责任服务，再用进程的打开文件和容器变更定位异常。能把投递日志和访问日志按秒对上，取决于事前保留了这些记录，也取决于重建时把旧容器和原始数据留了下来。
